# Database schema and version binding
Migration 011 adds script_capability_manifests (unique script_version_id, source_sha256, requested JSON, warnings), append-only script_capability_reviews (manifest_id, approved, denied, approved_at), and execution_capability_authorities (execution_id, immutable JSON snapshot). UPDATE triggers reject edits to all three history tables. Migration 012 adds a monotonic review_order so reviews with equal timestamps deterministically select the latest appended review, preserving original IDs/timestamps/content. Existing versions are left without new manifests and retain legacy profiles. New versions always get a new manifest and require fresh review, including unchanged capabilities.

Wire manifest: schemaVersion=1, id, scriptId, scriptVersionId, sourceSha256, requested[], warnings[], review|null. Review: id, approvedAt, approved[], denied[]. Requests carry capability, required, reason, constraints(maxCalls, optional entityTypes/playerNames). Unsupported requests are retained and flagged but cannot be approved. There is no fabricated approvedBy because the existing PoC has no identities. All-unchecked approval records an explicit denial of every request; Cancel records nothing. No-host versions request [] and need no permission review.

API endpoints: GET /api/scripts/:id/versions/:versionId/manifest; POST same path /reviews with only {manifestId,selected:[IDs]}; GET /api/scripts/capabilities/registry. Public execution requests cannot provide an authority snapshot. A run copies a review once; subsequent reviews affect future runs only. Version addition locks the parent script in a transaction to serialize version numbering. Script/version membership and source digest are checked before execution.
